01What KuttiDB is

KuttiDB is a lightweight, crash-recoverable event cache: zero-copy between local processes, network-accessible across machines, with cache, queues, exchanges and streams in one binary. No JVM, no Erlang, no external dependencies for a plaintext build.

Cache engine

Fast in-memory key/value + TTL

256-shard hash table, batching, pipelining, bounded memory with eviction, CRC-checked WAL & snapshots, shared-memory embedded mode.

Queue engine

Durable work queues

Durable declarations, publish confirms, manual ACK/NACK, visibility timeouts, redelivery flags, prefetch, dead-letter queues, retry delays, crash recovery. At-least-once.

Exchanges

Routing in front of queues

Direct, fanout and topic routing, an unnamed default exchange, alternate-exchange routing, unroutable reporting, durable bindings. Stateless — never stores messages.

Stream engine

Partitioned append logs

Topics with 1–256 partitions, keyed partition choice, replay from offsets, age/byte retention, persisted consumer-group offsets, lease-based groups.

Atomic cache + event

One commit id, two engines

put_and_publish, put_and_enqueue, delete_and_publish, update_and_emit: after recovery, both sides exist or neither does.

Anti-stampede + SWR

Single-flight loading, built in

First requester for a missing key loads it; others wait server-side. Plus stale-while-revalidate and refresh-ahead, and negative caching.

What it is not: it is not Redis, RabbitMQ or Kafka and speaks none of their wire protocols. It does not guarantee “no data loss” — evictable cache entries may be lost by policy, and a single node does not protect against disk or machine loss (replication is not implemented). There is no exactly-once claim anywhere.

02The big picture — how a request flows

Everything below lives in one process. Clients arrive over TCP or a Unix socket (or attach directly to shared memory when on the same, trusted host). A handful of event loops (not one thread per connection) parse the binary protocol and hand work to three logically separate engines, each with its own durability path.

Three engines, three WALs, one process. The commit coordinator is the only component allowed to write across two logs — that is what makes cache+event operations atomic.

Cache core details

Entries store key+value in one allocation; small entries come from 16 KiB slabs. TTLs are absolute Unix seconds — downtime never extends them. A global memory budget triggers random eviction (memcached-style). Evicted = gone, by policy.

Engines don’t share memory budgets

Queue messages never enter the cache’s eviction pool, and stream retention is separate accounting. A cache under pressure can never evict a durable queue message or a stream record.

Embedded mode (CEMBv3)

The shared file stores only fixed-width offsets, never pointers — each process may map it at a different address, so ASLR is safe. Locks recover when an owner process dies. Trusted local processes only.

03Write path & durability — when is a write “safe”?

Every mutation follows the same shape: parse → execute → append to a CRC-checked WAL → sync at the configured point → acknowledge. The two durability modes only change when the fsync happens for cache writes; queues, streams and atomic operations always fsync at their own acknowledgement points.

Crash recovery

Recovery replays the valid prefix of each WAL and idempotently truncates a torn or checksum-corrupt tail. Tests inject torn tails, corrupt CRCs, SIGKILL mid-write and disk exhaustion. Restoring the same backup twice is safe.

Snapshots ≠ backups

<WAL>.snap is a checkpoint that folds acknowledged cache state so the WAL stays small. A graceful shutdown writes a snapshot, then flushes and syncs the remaining log.

Single node, stated plainly

Acknowledged durable data survives process crashes and clean restarts on a healthy node. Disk loss, machine loss or site loss needs replication — which does not exist yet. Never describe this as zero-data-loss or HA.

04Atomic cache-plus-event commits — the differentiator

Invalidating a cache and notifying workers is normally two systems and two failure modes. KuttiDB commits a cache mutation and a queue/stream delivery under one durable commit id: after recovery, both sides exist or neither does. update_and_emit is conditional — an absent key commits nothing.

WAL folding defers while any transaction is inside its commit window, so a cache commit marker can never be folded away before its queue side is self-contained.

Use it for

Cache invalidation events (delete_and_publish), “state changed” broadcasts (put_and_publish), enqueuing work for the exact bytes you just cached (put_and_enqueue), and counters/state machines that must emit an event only when the update happened (update_and_emit — missing key → MISS, nothing committed).

From Python

r = db.put_and_publish("user:42", blob, exchange="events", routing_key="user.updated", ttl=60) returns {"tx_id": …, "routed": n}. Log tx_id — it is the durable transaction id recorded in both WALs.

05Durable queues — the life of a message

Queues are a separate engine with their own CRC-checked WAL. A durable message is removed only after its durable ACK record; everything else — visibility timeout, NACK requeue, dropped connection — makes it eligible for redelivery, which is flagged to the consumer. Delivery is at-least-once; design consumers to be idempotent.

python — durable work queue
# pip install path/to/clients (src/kuttidb_client.py)
from kuttidb_client import KuttiDBClient

with KuttiDBClient(port=7379) as db:
    db.queue_declare("jobs", durable=True, max_depth=10_000,
                     dead_letter_queue="jobs.dead", max_deliveries=5)
    msg_id = db.queue_publish("jobs", b"resize:123")   # confirmed after queue-WAL fsync

    delivery = db.queue_consume("jobs", visibility=30)  # lease for 30 s
    if delivery:
        try:
            process(delivery["value"])
            db.queue_ack("jobs", delivery["id"])         # durable ACK → message removed
        except Exception:
            db.queue_nack("jobs", delivery["id"], requeue=True, delay=5)

06Exchanges — routing without storage

An exchange never stores a message: a publish resolves the matching bound queues and writes one independent copy into each (a queue matching several bindings still gets one copy). Exchanges and queues live in separate namespaces. Routing is at-least-once and never silently lossy.

Fail-closed routing: if any target queue is full (or persistence fails), the whole publish errors before any copy is written. Unroutable is an outcome, not an error — status MISS + the exchange_unroutable counter.

python — topic routing with an alternate exchange
with KuttiDBClient(port=7379) as db:
    db.queue_declare("orders.all", durable=True)
    db.queue_declare("orders.eu",  durable=True)
    db.exchange_declare("events", type="topic", durable=True,
                        alternate_exchange="events.unroutable")
    db.exchange_bind("events", "orders.all", "orders.#")
    db.exchange_bind("events", "orders.eu",  "orders.eu.*")

    routed = db.exchange_publish("events", "orders.eu.paid", payload)
    if routed == 0:
        ...  # unroutable: went to the alternate exchange, or was reported MISS

07Streams — replayable partition logs

Streams are for replayable events, not work distribution: reading never removes a record — only retention does. Ordering is guaranteed only within a partition. Appends and group-offset commits are fsynced to the stream WAL before their response; fetch and commit are deliberately separate, so consumption is at-least-once.

"u-42" → FNV-1a hash → P1 keyless records → P0 P0 0 1 2 3 4 … oldest ← retention window → newest P1 0 1 2 3 4 5 ← new record lands here (offset 5) P2 0 1 2 3 billing @ P0: committed next-offset 3 → lag = 2 billing @ P1: committed next-offset 5 → lag = 0 Consumer group “billing” — lease-based stream_group_join(topic, group, lease=30) = join + heartbeat assignment: round-robin by connection id · m1 → P0, P2 · m2 → P1 generation increments on every membership change (rebalance signal) disconnect removes a member immediately · stream_group_leave drains server refuses commits from members that no longer own a partition Fetch ≠ commit stream_fetch(topic, partition, offset, max ≤ 1024) replays records stream_commit(topic, group, partition, next_offset) — durable, per group/partition. Process first, commit after → a crash in between replays: at-least-once by design, exactly-once is not claimed. Retention ignores consumer commits — stay inside the window. Storage note: retained records live in memory in front of one WAL — max_bytes bounds RAM as well as disk. Records are never removed by reading; only retention removes them.
python — keyed produce + group consume
with KuttiDBClient(port=7379) as db:
    db.stream_declare("payments", partitions=3, max_bytes=64*1024*1024, max_age=3600)

    r = db.stream_append("payments", payload, key="u-42")   # → {partition, offset}

    while True:
        a = db.stream_group_join("payments", "billing", lease=30)  # heartbeat each loop
        for p in a.partitions:
            off = db.stream_group_offset("payments", "billing", p) or 0
            recs = db.stream_fetch("payments", partition=p, offset=off, max_records=256)
            for rec in recs:
                handle(rec["value"])
                db.stream_commit("payments", "billing", p, rec["offset"] + 1)

08Anti-stampede — single-flight & stale-while-revalidate

When a hot key expires, a thousand clients normally thunder toward your database. KuttiDB coordinates the miss server-side: the first requester claims a lease and loads; everyone else waits for the same result. Negative answers are cached too, so absent keys don’t stampede either.

python — cache-aside without stampedes
def loader():
    data = expensive_db_call()          # runs once per miss, no matter how many waiters
    return json.dumps(data).encode()    # return None → negatively cached (absence)

value = db.get_or_load("hot-key", loader, ttl=60, lease=5, wait=10)

# stale-while-revalidate: serve stale instantly while one caller refreshes
db.put_swr("hot-key", value, ttl=60, stale_for=30, refresh_after=45)
result = db.get_or_load_swr("hot-key", loader, ttl=60, stale_for=30)

09Running it in production

KuttiDB ships as one executable with checked-in Docker and Kubernetes assets. Pick the shape that matches your durability needs — and remember the honest rule: durable mode is single-node durability. It survives process crashes and clean restarts, not disk or machine loss.

build + run (loopback, authenticated, durable)
make                 # builds kuttidb, kuttidb-bench, embedded lib (TLS=1 by default)
make test            # core, platform, queues, exchanges, clients, crash tests

umask 077
openssl rand -hex 32 > /run/kuttidb.token      # owner-only token file (1–1024 bytes)

./kuttidb 7379 /var/lib/kuttidb/kuttidb.wal 100 \
  --bind 127.0.0.1 \
  --auth-file /run/kuttidb.token \
  --durability always \
  --metrics-bind 127.0.0.1:9099

# positionals: [PORT [WAL [FSYNC_MS [UNIX_PATH [MAX_MEM_MB [EMBED_PATH]]]]]]
# cross untrusted networks? add --tls-cert / --tls-key  (or terminate TLS at your LB)
Flag intuition: FSYNC_MS only tunes the periodic cache mode — queues, streams and atomic ops always fsync at their own acknowledgement points. MAX_MEM_MB budgets the evictable cache only; queue/stream data is accounted separately (--stream-wal topics are RAM-bounded by their declared max_bytes).
docker compose (from the repo’s compose.yaml)
umask 077
head -c 32 /dev/urandom | base64 > ./kuttidb.token
KUTTIDB_AUTH_TOKEN_FILE="$PWD/kuttidb.token" docker compose up --build

The checked-in Compose file runs one durable instance: named volume at /var/lib/kuttidb, loopback-only ports 7379 + 9099, --durability always, auth token from a mounted secret, non-root image (uid 10001, plaintext build — terminate TLS at your ingress). docker stop sends SIGTERM → WALs are flushed and closed cleanly. Remove the volume only when intentionally discarding cache and queue state.

Do not scale to two containers. There is no replication: two writers on separate volumes are independent databases, not a cluster.
kubernetes — two supported shapes
# create the auth + metrics token secret first
kubectl create secret generic kuttidb-auth --from-file=token=./kuttidb.token

# durable: 1-replica StatefulSet, PVC, --durability always, auth on 0.0.0.0
kubectl apply -f deploy/kubernetes/durable-single-node.yaml

# or: evictable cache-only Deployment, no volume, disposable pods
kubectl apply -f deploy/kubernetes/ephemeral-cache.yaml

Durable StatefulSet gives you

PVC via volumeClaimTemplates at /var/lib/kuttidb · auth + metrics token from a secret (staged to a 0600 tmpfs by the entrypoint) · /ready + /live probes with a Bearer header (503 while any WAL is fail-closed) · non-root uid 10001, caps dropped, read-only rootfs.

Keep in mind

replicas must stay 1 on the durable manifest. Survives pod restarts and rescheduling onto a healthy node; not node/disk loss. Give terminationGracePeriodSeconds room for a final fsync (default 30 s is ample). Tune requests/limits to the working set.

Backup & restore

1 · Cold backup (the only supported kind)

kill -TERM $(pidof kuttidb) (or delete the pod) — graceful shutdown flushes and closes every engine — then tar -czf backup.tgz /var/lib/kuttidb.

2 · Restore

Copy the directory back, start with the same flags. Recovery replays each CRC-checked WAL and idempotently truncates torn tails — restoring twice is safe. Cross-host restore works (all state is file-based).

3 · What a backup restores

Acknowledged durable queue messages, stream records, group offsets and persisted cache records as of the last clean stop. Evictable entries that were evicted are gone. Live copies of open WALs are torn copies — don’t.

Upgrades

Upgrade = clean stop → replace binary → start on the same data directory. Protocol major.minor: different majors are refused at capability negotiation; higher minors are additive (clients check the feature bitset). A crash mid-upgrade resumes through the tested recovery path. Never run an older binary against data written by a newer one unless its release notes say formats are unchanged.

11Honest limits, sizing & alternatives

The durability contract, one table

Data classAcknowledgement pointGuarantee after crash / restart
Evictable cache entryper durability mode (periodic = batched)Best effort — may be evicted by policy, may be lost inside the periodic window.
Cache entry (always)fsync of cache WAL record before responsePresent after recovery — healthy single node.
Durable queue messagefsync of queue WAL publish recordPresent; delivery is at-least-once.
Durable ACKfsync of queue WAL ACK recordMessage not removed before its ACK is durable.
Stream record / offset commitfsync of stream WAL recordSame single-node process-crash guarantee.
Atomic cache + eventfsync of the cache WAL commit markerBoth sides visible after recovery, or neither.
A single node does not protect against: disk loss (both WALs share one volume) · machine/node loss (no replication) · mid-log media corruption (CRC failure = end-of-log). Replication with a documented consensus design is a prerequisite for any availability claim beyond a healthy single node.

When to use something else

ChooseWhen
RedisYou need rich data structures (lists, hashes, sorted sets, Lua) or its ecosystem modules. KuttiDB’s cache is deliberately smaller: key/value + TTL + batch + single-flight.
RabbitMQYou need AMQP semantics, complex topologies, or a mature broker ecosystem. KuttiDB queues cover the core work-queue contract natively — not AMQP.
KafkaYou need its retention ecosystem, exactly-once transactions, log compaction, or Kafka tooling. KuttiDB streams are a focused, at-least-once subset — use native clients or a bridge.
SQLiteYou need queries, secondary indexes, relational integrity. KuttiDB is not a database in that sense.
